# TTL policy

Loaded on demand by the `aws-grounding-cache` skill. Defines the time-to-live windows per `ttl-class` and the read-side behaviour when an entry is past its window.

## TTL windows

| `ttl-class` | Window     | Rationale                                                                                                  |
| ----------- | ---------- | ---------------------------------------------------------------------------------------------------------- |
| `pricing`   | 30 days    | Pricing API values change with billing-model updates and regional adjustments; 30 days is the safe window. |
| `quota`     | 30 days    | Default quotas drift as AWS adjusts service limits; 30 days catches most shifts without daily churn.       |
| `api-shape` | 90 days    | Stable interfaces — request/response fields, parameter shapes, error codes — change slowly.                |
| `region`    | 90 days    | Region availability and service-to-region matrices change quarterly at most.                               |
| `immutable` | indefinite | ARN format, foundational identifiers, structural constants — these do not change.                          |

## Picking the right ttl-class on write

The writer must classify the response into one of the five values. The classification is determined by the _content_ of the cached value, not by the MCP tool that produced it.

- A pricing number → `pricing`.
- A service quota or limit → `quota`.
- A request parameter list, response field, or error enum → `api-shape`.
- A region availability statement or service-region matrix → `region`.
- An ARN format, identifier prefix, or constant string → `immutable`.

When a single response covers multiple classes (e.g., a doc page that includes pricing and quota), split the cached entry by the dominant class and let the other claims be re-fetched as needed. Do not pick the longest TTL just to avoid re-fetches.

## Read-side behaviour

When a reader looks up an entry:

1. Compare `now()` (UTC) to `entry.retrieved + window(entry.ttl-class)`.
2. If `now()` is within the window: return the entry as fresh.
3. If `now()` is past the window: return the entry with a stale flag. The caller decides:
   - Discovery agent: re-fetch immediately and overwrite.
   - Reviewer agent: surface the stale flag in the audit log; do not auto-refresh in a read-only session.
   - Implementation agent: re-fetch if the value is load-bearing for the current task; otherwise note the staleness.
4. `immutable` entries are never stale.

## Why TTL is not configurable

The five classes and their windows are baked in. Configurability would tempt callers to extend windows to avoid MCP calls, which is precisely the failure mode the cache is designed to prevent. A v0.2 enhancement could add a per-feature override (with audit trail) gated on a documented decision; until then, no overrides.

## Interaction with degraded MCP servers

If an MCP server is degraded and the agent cannot re-fetch a stale entry:

1. The cache returns the stale value with both stale and degraded flags.
2. The caller emits `grounding-deferred` (the same marker used for un-grounded claims).
3. The orchestrator's merge contract surfaces the deferral under `## Degraded signals`.

The caller does **not** silently use the stale value as if fresh. Better to surface the gap than to write a spec on values nobody has confirmed in 90 days.

## Write-side timestamp discipline

The `retrieved` timestamp is generated by the cache write path from the system clock at the moment of write, in UTC, ISO-8601 format. The caller does not supply this value; trusting agent-supplied timestamps would let a misconfigured caller defeat TTL by claiming yesterday's response is "current".
