# Ledger schema

Loaded on demand by the `aws-grounding-cache` skill. Defines the canonical structure of `.claude/specs/<feature>/.grounding-ledger.json` and the rules each entry must satisfy.

## Top-level structure

The ledger is a single JSON object with two keys:

```json
{
  "entries": {},
  "conflict_resolution": []
}
```

- `entries` is an object keyed by `<server>:<short-key>`. Each value is a single ledger entry (schema below).
- `conflict_resolution` is an array of merge-contract conflict logs, appended in chronological order.

The starter file lives at `assets/grounding-ledger.json.tmpl` and is copied into a feature directory the first time a write occurs.

## Entry schema

Every entry under `entries` has exactly the following keys:

| Key              | Type    | Required | Description                                                                               |
| ---------------- | ------- | -------- | ----------------------------------------------------------------------------------------- |
| `server`         | string  | yes      | One of `kb`, `iac`, `cost`, `sec`, `iam`, `cw`. Must match the prefix of the entry key.   |
| `tool`           | string  | yes      | The MCP tool name that produced the result (e.g., `read_documentation`, `get_pricing`).   |
| `query`          | string  | yes      | The canonicalised query string used to derive the short-key.                              |
| `retrieved`      | string  | yes      | ISO-8601 UTC timestamp of the MCP response, generated by the write path (not the caller). |
| `result_summary` | string  | yes      | Short human-readable summary of the result, ≤500 chars. Not the raw payload.              |
| `ttl-class`      | string  | yes      | One of `pricing`, `quota`, `api-shape`, `region`, `immutable`.                            |
| `short_key_ext`  | boolean | no       | Set to `true` when the short-key was extended to 12 hex chars due to a collision.         |

Unknown keys are forbidden. Extra keys are an error in the writer.

## Example entry

```json
{
  "entries": {
    "kb:a3f2b1c4": {
      "server": "kb",
      "tool": "read_documentation",
      "query": "lambda concurrency limits eu-west-1",
      "retrieved": "2026-05-02T08:14:03Z",
      "result_summary": "Default unreserved-concurrency quota is 1000 per region; raises available via service quota request.",
      "ttl-class": "quota"
    },
    "cost:b7e2d019": {
      "server": "cost",
      "tool": "get_pricing",
      "query": "s3 standard storage eu-west-1 first-50-tb-month",
      "retrieved": "2026-05-02T08:14:11Z",
      "result_summary": "$0.023 per GB-month for first 50TB in eu-west-1.",
      "ttl-class": "pricing"
    }
  },
  "conflict_resolution": []
}
```

## Conflict-resolution log entries

Each entry in the `conflict_resolution` array has:

| Key           | Type     | Required | Description                                                          |
| ------------- | -------- | -------- | -------------------------------------------------------------------- |
| `timestamp`   | string   | yes      | ISO-8601 UTC.                                                        |
| `specialists` | string[] | yes      | Names of the specialists involved in the conflict.                   |
| `options`     | string[] | yes      | The competing options.                                               |
| `rule`        | string   | no       | The merge-contract priority rule that resolved the conflict, if any. |
| `chosen`      | string   | no       | The selected option. Omit when the conflict was raised to the user.  |
| `status`      | string   | yes      | `resolved` or `unresolved`.                                          |

Logs are append-only; existing entries are never edited.

## Validation rules

1. The ledger root must be a JSON object with the two top-level keys above.
2. Each `entries` key must match the regex `^(kb|iac|cost|sec|iam|cw):[0-9a-f]{8}([0-9a-f]{4})?$` — base 8-char short-key, optional 4-char collision extension.
3. The `server` field of an entry must equal the prefix of the entry key.
4. `ttl-class` must be one of the five allowed values; any other value invalidates the entry.
5. `result_summary` ≤ 500 chars. Truncate at write time if upstream returns more.
6. No raw payload is stored. The `result_summary` is a _summary_, not the full response.
7. Redaction must have run on `result_summary` before write. The on-disk value contains no secrets.

## What is NOT in the schema

- No URLs to upstream sources. The `query` plus the `tool` are sufficient to re-derive the source.
- No version field on entries. Schema migrations are handled by reading the absence of expected keys, not by versioning each entry.
- No payload checksums. The short-key already encodes a content-derived identity.
